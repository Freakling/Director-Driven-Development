# From proof of concept to production in an enterprise: what the operating envelope needs, where people and process fail, and what SaaSAllTheThings brings
R6 · Informs: - · Verified as of 2026-10-21 · Size: M

## Question and assumptions
Question: what does production readiness mean for a business-critical enterprise system beyond the code; what do the main breach and incident reports say about how people, process and infrastructure hygiene fail as against code vulnerabilities; what do the AI coding tools' security features cover at those layers and what do enterprises use instead; and what does SaaSAllTheThings do, at its latest release, with an uploaded control framework such as the ISF Standard of Good Practice. Which of "a full supply-chain view, more security and easier compliance proof than others" holds on its records, and which needs a deployment or an audit? R5's tool table and conclusion are built on, not repeated.

Assumptions:
- "Production readiness" is read as the operating envelope around the code: what an enterprise go-live review and an auditor ask about. No single authoritative checklist exists. I used the Azure Well-Architected pillars, GDPR Articles 32 and 33, ISO/IEC 27002:2022 control titles and NIST CSF 2.0 only to name the areas, not to claim a mapping.
- Azure is the platform because SaaSAllTheThings is. Microsoft pages were read on 2026-10-21; their page dates are in Sources.
- SaaSAllTheThings is read from the read-only checkout in `.app-director/state/frameworks/SaaSAllTheThings`. `VERSION` says 0.9.1, `CHANGELOG.md` heads with 0.9.1 (2026-10-18) and has no Unreleased section, and GitHub's latest release page shows v0.9.1 ("17 Oct", year not shown). I could not run git, so I did not prove the folder equals the tag. Nothing was run: not the check, not `selftest.sh`. "Not found" means not found by listing and searching that folder.
- "Holds on the records" means the v0.9.1 files state it, or reading the code shows it. "Needs a deployment or an audit" means only a running system, a test on it, or a third party can show it.
- Report pages were read through fetch tools that summarise them. The full DBIR PDF exceeded the fetch limit and the executive summary PDFs came back unreadable. Where a figure comes from a secondary summary, the Sources table says so.
- The ISF text itself was not available to me, only its public page. The note describes what the framework does with any control framework text placed in the repository.
- Technical guidance, not legal advice. Legal, privacy, risk and audit owners should confirm the GDPR, ISO and customer-framework readings.

## Conclusion
Most of the operating envelope (identity, network exposure, configuration, recovery, monitoring, access reviews, audit evidence) is a property of a running system and the people who run it, so a repository can hold its requirements, design and infrastructure code but cannot prove it. The incident reports point the same way: exploitation of vulnerabilities is now the top entry point (31 percent of breaches in DBIR 2026, 32 percent of identifiable vectors in M-Trends 2026), but that is flaws in deployed products left exposed or unpatched, no report read separates flaws in the victim's own code, and the rest is identity, people, third parties and slow detection. AI coding tools' security features cover source code, and in two cases secrets; none of the pages read cover network exposure, access, recovery or audit evidence, which enterprises cover with Azure Policy at deploy time, Defender for Cloud at run time and IaC scanners in the pull request. SaaSAllTheThings v0.9.1 holds on its records for a design-time chain (assessment, five-plus workshops, requirements and a named control framework in the PRD and `compliance/`, ADRs, decision log, one item per commit) and for nine architecture rules in the check with an ADR-only exception path; it ships no network-isolation rule, no dependency or supply-chain tooling, no IaC scanning, no DR design, no CI, no control-to-rule mapping, and no audit. So "a full supply-chain view" does not hold (a delivery-chain view does), "more security than others" does not hold as stated (a narrower claim does), and "easier compliance proof" is plausible for design-stage evidence but unproven until a deployment and an audit. Confidence: high on what the release ships; medium on the report figures (several are secondary); low on any comparison with other tools.

## 1. What production readiness means beyond the code
Areas, with the source that names each:
- **Infrastructure and change:** environments as code, reviewed change, no drift (Azure Well-Architected: Operational Excellence "standards, comprehensive monitoring, and safe deployment practices"; Reliability "resiliency, availability, recovery"; Security "data protection, threat detection, and mitigation").
- **Monitoring and operations:** observability, alert routes, incident response. GDPR Article 33 sets 72 hours from awareness for the controller to notify, and requires the processor to notify the controller "without undue delay", so detection and escalation must exist before go-live.
- **Compliance audits:** evidence that controls operated over time, not only a design. Defender for Cloud's compliance dashboard marks controls it cannot assess automatically, so part of the evidence is manual.
- **PII:** classification, minimisation, retention, residency, deletion. GDPR Article 32(1)(a): "pseudonymisation and encryption of personal data".
- **Access:** identities, MFA, least privilege, just-in-time access to production, reviews. Microsoft: in every service model the customer keeps "Customer data", "Configurations and settings" and "Identities and users", and in PaaS the application is shared ("code security" is yours).
- **Business continuity and disaster recovery:** recovery point and time, backups, restore tests. GDPR Article 32(1)(c) and (d): restore availability and access "in a timely manner" and "a process for regularly testing" the measures.
- **Cloud networking:** public network access off, private endpoints, local authentication off, egress control. Microsoft Azure Policy has built-in Audit or Deny definitions for public network access on Service Bus, Cosmos DB and Key Vault.
- **Supply chain:** dependencies, third parties, pipeline identity.

Judgment: each area is shown by a running system, its logs and a test on it. A repository can hold the requirement, the design and the infrastructure code; it cannot hold the proof.

## 4. What SaaSAllTheThings v0.9.1 does with a control framework
### 4.1 The path, with files
1. **Placement.** Nothing ingests or parses the framework. The human names the security framework and control frameworks in `product/director-brief.md` section 10 (columns: version or edition, what applies, evidence expected and from whom), and puts the requirements text or the customer's own control list in `compliance/`. `project/` does not seed that folder; `ONBOARDING.md` (Your own product brief, step 5) tells the human to use it, and `architect.md` reads it "if present". Onboarding records the named frameworks under PRD › Data and Compliance and never claims a requirement is met because the brief names a framework.
2. **Assessment** (`procedures/assess.md`, read only): reads the brief first, marks `(from the brief)` or `(inferred, please confirm)`, scores nine dimensions 0 to 3 (including configuration and secrets, identity, delivery and operations), builds a staged roadmap, then picks workshops. Report shape: `templates/assessment.md`.
3. **Workshops** (`.satt/workshops/`; notes to `assessment/workshops/YYYY-MM-DD-<name>.md`): vision (constraints: deadline, budget, compliance, the customer's Azure governance), tenancy-identity (security officer and data protection officer or legal attend; region, retention, personal data, audit, export and deletion; a data map), integration (access and credentials: consent, outbound-only connector or VPN; ADR for a stored credential), operations (access for people with just-in-time for production, managed identities, Key Vault, "threat review of the target picture", recovery point and time, support, cost; it asks the governance owner for the landing zone and its rules beforehand), planning (stage order, owners and dates). Outputs go to PRD sections, `decisions.md`, ADR drafts and human items in `TASKS.md`.
4. **Architecture sessions** (`procedures/architect.md`): Prepare reads `compliance/` and PRD › Data and Compliance and flags a conflict between a requirement and the reference. Propose applies a standing check (OWASP Top 10, least privilege, defence in depth, zero trust, data minimisation, "any standard named in the compliance requirements") and each option states security and compliance impact. Only the human accepts the ADR.
5. **Research** (`procedures/research.md`, `research-domain.md`): the customer's security framework is Tier 1; each requirement is traced to a control and labelled direct, partial, interpretive or unverified; the shared-responsibility boundary is named; a requirement is never inferred as met from a control; text from `compliance/` never enters a public search.
6. **Not found:** `build.md`, `review.md`, `align.md`, `release.md` and the check do not read `compliance/`. No rule or test is traced to a control id, and no mapping table is seeded. Items point to PRD headings (`PRD:` field), not control ids. The ISF Standard of Good Practice is not named anywhere in the release; ISO 27001, SOC 2, GDPR and similar appear only as examples. The framework is anchored in the customer's security framework as a process and a record place; it is not compliance as code.
7. **ISF note:** the ISF page says SOGP 2026 launched "exclusively to ISF Members", with a public release planned later in 2026. Its terms of use were not read. Whether a member may place the text in a repository an AI assistant reads is a licence question for the member.

### 4.3 The check and the ADR path
- **Holds (code inspection of `framework/tools/archcheck.awk` and `check.sh`; `selftest.sh` carries seeded faults for all nine rules; not run):** nine rules (`layers`, `domain-purity`, `tenant-source`, `tenant-branching`, `secrets`, `file-size`, `host-size`, `message-version`, `cost-sku`); exit 0, 1 or 3, and exit 3 never reads as pass; only an ADR with `Status: accepted` excuses a failure; an exception must name a rule and a folder or file, and a bare `**` is refused; a proposed ADR's exceptions do not apply; an ADR without a Status line fails; an exception that excuses nothing is noted.
- **Limits:** it reads text, skips comments, not strings; the reference itself calls it "a strong net, not a proof". It never calls Azure. The gate is a local pre-commit hook and, in Claude Code, a stop hook; no CI ships. `--no-verify` is blocked by a Claude Code hook only. "Only the human accepts an ADR" is a rule plus a Claude Code hook that asks when an Edit or Write contains `Status: accepted`; the hook says it is "a strong safety net, not a guarantee". The status is a plain text line, so a person reviewing the diff (branch rules, pull request) is what makes it binding, and the framework does not set that up. With `--tools none` there are no hooks.

### 4.4 Records a compliance reviewer can read
Committed in the app: `product/prd.md` (current requirements, Data and Compliance, Service Levels), `product/decisions.md` (append-only, why and source), `adr/` (context, options, decision, consequences, check exceptions, status), `TASKS.md` (items with `PRD:` and `ADR:` and outcomes tagged test, check or demo), commits (one item, one commit, id in the message), `integrations/<system>/contract.md`, `assessment/` (reports and workshop notes, roles not names), `validation/` (acceptance checks with build and environment), `product/research/` (notes with sources, tiers, confidence, verified date), `resets/`, AGENTS.md › Architecture. Not committed: check logs and review diffs (`.satt/state/`).

## Options and trade-offs (the message)
| Option | Means | Risk |
|---|---|---|
| A. Keep the three claims | "Full supply-chain view, more security, easier compliance proof" | The first two fail on the records; the third has no comparison |
| B. Narrow to the records | "Your security and architecture requirements become design records and a build gate; operating evidence comes from your deployment" | Holds. Needs the limits stated plainly |
| C. Say nothing on production until a pilot | Safe | Loses the strongest differentiator |
| D. Earn it | Pilot deployment with Azure Policy and Defender, then an audit or measured comparison | Costs time and Azure access; the only route to the stronger claims |

## Recommendation
B now, D as the route to anything stronger. Wording that holds: "A check that fails the build when architecture and security requirements are broken, with exceptions only through a decision record you accept"; "your control framework and requirements live in the repository and every architecture session reads them"; "every decision and change leaves a record a reviewer can read"; "the running system, not the repository, provides the operating evidence." Wording that would not hold: "full supply-chain view", "more secure than others", "compliance proof", "cannot exfiltrate", "production-ready".

Builder items to consider (proposals, nothing run):
1. A network posture topic plus a check rule on Bicep (public network access, local authentication), and a plain statement in `cost.md` that private-only needs Service Bus Premium and therefore an ADR with a `cost-sku` exception.
2. A shipped CI workflow that keeps check output as an artifact, so the gate leaves evidence off the developer's machine.
3. A seeded `compliance/` mapping table (control id, requirement, rule or ADR or test, label direct, partial, interpretive or unverified, evidence location) that `review.md` and `align.md` read.
4. A continuity topic from PRD Service Levels to backup and region choice, with a restore-test item.
5. Dependency view: wire GitHub dependency graph and SBOM export, or state it is the customer's pipeline.
6. A pilot (human with Azure access): deploy the sample app to a sandbox with Azure Policy Deny assignments and Defender for Cloud, test from outside, record results.

This would change if a pilot or an audit produces evidence, if a comparison measures a difference, or if the full report PDFs contradict the secondary figures used here.
